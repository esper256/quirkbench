# Quirkbench 1.2 plan

Make investigations cheaper in agent effort and human waiting. Keep the working
recovery, deployment and command model. This is a revisable plan, not new product
requirements or a claim that these features exist.

## Evidence informing priorities

The October 23 Acer session recorded 486 MCP calls and 181 commands. One results
response was 611 KB. Session setup appeared in 55 command bodies; 89 retained
uploads included 57 shell/Python scripts. These are observations, not all waste.
Cached deployment took 22 seconds versus 13 minutes initially; corrected candidate
preparation reused 135 layers. Prioritize interaction costs over another deployment
redesign. Builds and tests overlapped; do not sum their durations as elapsed time.

## Implementation order

1. **Compact evidence access.** Make `run_results` a summary of outcome, receipt,
   collection failures, counts and size. Replace duplicate file lists with one
   paginated manifest; page command/transfer details too. Reuse `saved_output_read`
   for bounded reads and add tail access there if useful. A thousand-file run must
   produce a small default response while all evidence remains accessible.

2. **Clear diagnostics and baseline identity.** Accept the recorded baseline digest
   as equivalent to its original reference without refreshing a moving tag. Separate
   inventory tool exit codes from warnings and partial reads. Attribute diagnostics
   to the run, boot and recovery/candidate environment; explicitly report missing
   candidate logs. Use existing early-boot collection where feasible, without
   promising evidence that cannot survive a failure before storage is available.

3. **Existing-session command access.** Inspect available login sessions and allow
   explicit execution as the selected session's user with the appropriate environment.
   Keep normal command IDs, deadlines and output handling. Report the selected
   session and fail clearly when unavailable. No automatic user creation, autologin,
   desktop manager or audio-specific commands.

4. **Less file-transfer plumbing.** Support bounded batch uploads through the existing
   SFTP mechanism, with per-file outcomes. Explain upload-and-execute using existing
   sequences before adding another combined tool. Preserve ordinary single-file
   calls and safe publication; do not build another execution system.

5. **Human-assisted tests.** Extend existing notifications with a short request,
   explicit readiness, acknowledgment and cancellation. The agent verifies its
   collector before marking the request ready; late responses remain identifiable.
   Preserve desktop visibility. Expose current sleep inhibitors and their known
   lifetime; keep screen blanking separate. Do not silently inhibit deliberate
   suspend tests or automatically repeat attention sounds.

6. **Subtract noise and improve guidance.** Remove repeated general warnings from
   successful responses; keep actionable restrictions and evidence limitations.
   Limit unchanged-response analysis to appropriate reads/waits. Document preparing
   candidates before borrowing a target, reusing build output, workload hashes/options,
   and cleanup of agent-launched containers. Do not add a kernel-build framework,
   container supervisor or growing catalogue of subsystem-specific probes.

## Sequences: retain in 1.2, decide in 1.3

No sequence calls were recorded in the first Acer session. That does not establish
that the feature lacks value. Make its purpose, supported actions, failure behavior
and examples prominent in the agent guide: upload/start/wait and prepare/deploy/boot
when no intermediate inspection is needed. Individual calls remain equally valid.

For the next session, ensure the agent has read this explanation. Review existing
call records and ask why it chose or avoided sequences; do not require their use.
If they remain unused despite awareness, plan their removal in 1.3 in favor of a
few demonstrated shortcuts over existing operations. Do not expand the sequence
language or introduce competing orchestration in 1.2.

## Verification and completion

Use short integration journeys with real application code, temporary files and
local connections. Substitute expensive OS actions. Cover bounded results, partial
inventory, equivalent baseline references, explicit session selection, transfer
failure and late/cancelled human requests. No routine image builds or QEMU.

In the next authorized target session, verify the already-implemented package
removals plus replacement kernel, finished initramfs, boot and reconnection. Check
the new audio fixture at comfortable volume before reusing thresholds. These are
outstanding real-world checks, not reasons to rebuild the architecture.

Keep preparation/deployment/boot separately callable, explicit pause/force-stop,
unknown connection outcomes, restricted recovery access and final evidence receipt.
Compare cold and repeated timings, response sizes, avoidable calls and human
interventions. No migrations or owner-data reset. Update affected guide/mockups
with implementation; ask before substantial complexity or capability loss.

Also profile the fast suite's slow tests during implementation. Replace avoidable
sleeps, reconnect delays and OS work at the smallest useful boundary. Keep real
application behavior and deliberate timeout/termination checks; compare measured
before/after durations rather than weakening assertions for speed.

## Implementation status

Software changes are implemented with fast integration coverage. Existing sequences
remain supported and documented. No owner data was reset. Updated target tools are
needed for session selection and human requests; older tools reject these operations
clearly. Recovery rebuild, flashing and the target checks above remain separate,
authorized work. This is not a release or proof of hardware boot.
